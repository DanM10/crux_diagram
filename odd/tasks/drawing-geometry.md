- L1 (2026-11-23, user): "antes de seguir con ci, vamos con otra historia de usuario, para ello crea una nueva rama desde el main, tenemos: /tmp/crux-diagram-geometria.md." Story, verbatim:

    # Requerimiento para crux_diagram: geometría de dibujo exportable
    
    ## 1. Contexto
    
    Un backend (Spring Boot, Java2D) genera la imagen PNG de un dibujo sin
    navegador, para insertarla en reportes. No debe repetir la geometría que ya
    calcula el editor ni depender de una biblioteca Java del formato.
    
    Flujo previsto:
    
    1. El editor (`@crux-diagram/react`) edita el documento v1.
    2. Al guardar, el front calcula la **geometría de dibujo** con `core` y la envía
       junto con el documento, como un JSON aparte.
    3. El backend guarda los dos. El documento vuelve al editor; la geometría solo
       la lee el backend para dibujar (solo pinta, no calcula).
    
    La geometría **no** va dentro del documento: `parse` descarta los campos
    desconocidos (FMT-009) y el formato v1 no debe cambiar.
    
    ## 2. Situación actual (0.1.0)
    
    - `core` exporta `anchorPositionOf`, `labelFontSize`, `arrowheadSize` y
      `DEFAULT_JOINT_STYLE`.
    - `leaderLineStart` y `arrowheadPoints` existen en `geometry/joints.js`, pero no
      se exportan desde `index`.
    - El cálculo completo de cada joint vive en **`react`**, no en `core`:
      `render/scene.js` → `placeJoints(document, style, measurer)` y
      `jointGraphics(placement, style, labelSize)`. Ahí se resuelven el anclaje, la
      caja de la etiqueta, la posición del texto, la línea (o su ausencia) y la
      punta de flecha.
    
    ## 3. Qué se necesita
    
    ### 3.1. `core`: función pública `computeGeometry`
    
    Mover a `core` la lógica de `placeJoints` + `jointGraphics` (sin Konva) y
    exponerla:
    
    ```ts
    export function computeGeometry(
      document: DrawingDocument,
      options: { measurer: TextMeasurer; style?: JointStyle },
    ): DrawingGeometry;
    ```
    
    - `style` por defecto: `DEFAULT_JOINT_STYLE`.
    - `react` pasa a usar esta misma función para dibujar, de modo que la geometría
      exportada sea **exactamente** la que se ve en pantalla. Una sola
      implementación, no dos.
    - Es pura y determinista para un mismo `measurer`.
    
    ### 3.2. Estructura de salida
    
    Debe bastar para dibujar los joints sin conocer reglas del formato: primitivas
    listas para pintar, en unidades del canvas.
    
    ```ts
    interface DrawingGeometry {
      geometryVersion: 1;
      canvas: { width: number; height: number };
      joints: JointGeometry[];
    }
    
    interface JointGeometry {
      id: string;                 // joint.id del documento
      anchor: Point;              // punto del anclaje en canvas
      labelRect: Rect;            // caja de la etiqueta, con padding incluido
      text: {
        value: string;            // joint.name
        x: number;                // esquina superior izquierda del texto
        y: number;
        width: number;            // tamaño medido por el measurer
        height: number;
        fontSize: number;         // 30 / 34 / 38 según labelSize
        fontFamily: string;       // "Arial" (LABEL_FONT_FAMILY)
        bold: boolean;
        color: number;            // ARGB
      };
      line: { from: Point; to: Point } | null;  // de leaderStart a la base de la punta
      arrowhead: [Point, Point, Point] | null;  // [tip, izq, der]
      lineWidth: number;          // 2.5 por defecto
      lineColor: number;          // ARGB
    }
    ```
    
    Reglas que hoy aplica `jointGraphics` y que deben conservarse:
    
    - `jointDisplay.visible === false` → `joints: []`.
    - Joint cuya figura o anclaje no existe → se omite.
    - Anclaje dentro de la etiqueta, o `leaderStart` igual al anclaje → `line` y
      `arrowhead` en `null`.
    - Línea más corta que la punta de flecha → `line` en `null`, pero `arrowhead`
      sí.
    
    Se incluye `geometryVersion` para poder cambiar la estructura sin ambigüedad.
    
    ### 3.3. Exportaciones adicionales en `core`
    
    - `leaderLineStart`, `arrowheadPoints`, `Rect` y `JointStyle` (tipo).
    - `LABEL_FONT_FAMILY` (hoy está en `react`).
    - `validateGeometry(document, geometry)`: comprueba la **forma**. Un registro
      por cada joint dibujable, con los mismos ids; números finitos; `labelRect`
      con medidas no negativas; `arrowhead` de tres puntos o `null`. Con códigos de
      error estables, como `validate`. Sirve de referencia para reimplementar la
      misma verificación en el backend.
    
    ### 3.4. `react`: acceso desde el editor
    
    Para que el front no tenga que replicar la configuración del editor:
    
    - `DrawingEditorHandle.getGeometry(): DrawingGeometry`. Usa el mismo
      `measurer` y estilo que el editor (incluida la config de
      `DrawingEditorConfig`).
    
    ### 3.5. Figuras
    
    Las figuras **no** necesitan geometría: el backend las dibuja desde el
    documento (`center`, `size`, `rotation`, `fill`, `stroke`, `strokeWidth`).
    Solo hace falta documentar en la spec la regla que ya aplica
    `shapeNodeProps`: un relleno o trazo con alfa 0, o con ancho 0, no se pinta.
    
    Opcional: si se prefiere que el backend sea un pintor totalmente "tonto",
    `DrawingGeometry` puede incluir también `shapes` como primitivas
    (rectángulo/elipse con centro, tamaño, rotación en radianes y colores ARGB ya
    resueltos).
    
    ## 4. Pruebas
    
    - Fixtures compartidas en `spec/fixtures`: documento → geometría esperada,
      usando `ApproximateTextMeasurer` para que el resultado sea determinista.
    - Casos: joint normal; anclaje dentro de la etiqueta; línea más corta que la
      punta; joint con figura inexistente; `visible: false`; los tres
      `labelSize`; figuras rotadas.
    - Test en `react` que confirme que lo que dibuja el editor sale de
      `computeGeometry` (misma salida para el mismo documento y measurer).
    
    ## 5. Fuera de alcance
    
    - Cambios al formato v1 o a `schemaVersion`.
    - Cambios al paquete Flutter. No es necesario, porque el móvil solo lee
      documentos. Si en el futuro debe guardar, necesitará la misma función.
    - Render en el servidor. Eso lo implementa el backend con Java2D.
    
    ## 6. Entrega
    
    - Publicar `@crux-diagram/core` y `@crux-diagram/react` 0.2.0, con
      `computeGeometry`, las exportaciones de §3.3 y `getGeometry` en el editor.
    - Documentar la estructura de §3.2 en la spec (por ejemplo,
      `spec/06-spec-geometria.md`).
    - Nota para consumidores: el texto se mide con la fuente del navegador
      (`Arial`). Un render del lado del servidor debe centrar el texto dentro de
      `labelRect` con una fuente equivalente, porque el ancho puede variar unos
      píxeles.
